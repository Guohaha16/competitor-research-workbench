# Public research protocol

Use this protocol for a new competitor or a time-sensitive refresh.

## Evidence pass

Start with the product's official site, pricing, changelog/release notes, help center, app-store listing, public demos, and company announcements. Add independent reviews or community reports when they reveal usage context or friction. Search broadly enough to cover the user's question, but do not claim to have found “all information.”

For each useful item retain:

- title, URL, publisher, publish date when available, and access date;
- evidence type: `official`, `hands_on`, `third_party`, or `community`;
- the claim supported and a short paraphrase;
- screenshot path when the interface or visual hierarchy is material;
- confidence: `high`, `medium`, or `low`.

Capture screenshots at decision-relevant states, not every page. Prefer: landing/value proposition, pricing, main navigation, key feature entry, completed result, permission/share flow, upgrade boundary, and important error/empty states.

## Analysis pass

Produce these connected views:

1. **Positioning:** audience, primary job, value proposition, differentiators, distribution and monetization signals.
2. **Feature framework:** `domain > capability > atomic feature`, with competitor coverage and evidence links.
3. **Journey:** trigger, entry, activation, repeated value, collaboration/retention, expansion or payment.
4. **Comparison:** parity, meaningful implementation differences, gaps, switching costs, and risks.
5. **Direction:** 3–5 likely developments, each tied to observed signals and marked as inference.

Avoid feature-count scoring. Weight capabilities by target user value, workflow importance, maturity, and evidence quality.

## Update behavior

When a prior workspace exists, preserve stable IDs. Merge new evidence into existing nodes, add variants when behavior differs, and mark stale or contradicted claims instead of silently deleting them.
